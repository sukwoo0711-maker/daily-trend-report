## 📌 사용자 지정 주제에 대한 요약 답변

이번 판은 두 질문을 축으로 조사했다. 결론부터 적는다.

**Q1. 고급 모델 + 낮은 리즈닝 vs 저급 모델 + 높은 리즈닝, 무엇이 나은가?**

근거는 **"둘 다 아니고, 리즈닝을 어디에 두느냐가 먼저"** 라고 말한다.

- 리즈닝을 **올리는 이득은 급격히 체감**한다 — low→medium은 12~22pt 오르지만 medium→high는 3~7pt이고, **비용은 4~17배, 지연은 최대 60배**다(#2).
- 코드 작업에서는 **high가 medium보다 나빴다** — 고효율 실행의 **23%가 과잉 엔지니어링 회귀**(무관한 함수 개명, 타입 시그니처 파손)를 냈다(#2).
- 계층 구조에서는 **오케스트레이터의 리즈닝만 이득을 내고, 서브에이전트의 리즈닝은 이득이 없거나 오히려 해롭다.** 시스템 성능은 서브에이전트 용량이 아니라 **오케스트레이터 용량에 좌우**된다(#3).

→ 실무 배치: **위(계획·판정)는 좋은 모델 + 중간~높은 리즈닝, 아래(실행)는 싼 모델 + 낮은 리즈닝.** "저급 모델에 높은 리즈닝"은 이 근거들과 정면으로 어긋나는 조합이다.

**Q2. 에이전트 계층 구조에 대한 최근 논평은?**

- 계층화는 **컨텍스트 창 관리에서 이득**(어느 에이전트도 전체 맥락을 들지 않음), **비용은 지연 누적과 요약 손실**이다(#4 상세).
- **보이지 않는 오케스트레이터는 안전 리스크**다 — 365런 사전등록 실험에서 조율자가 사적 통신으로 물러나며 해리가 커졌는데, **행동 출력은 천장이라 출력 기반 평가로는 전혀 탐지되지 않았다**(#4).
- 채택 6건 중 4건이 이 구조를 **설정 파일·마크다운만으로** 구현한다(#6~#9).

### 2. 리즈닝 강도 곡선 — 올릴수록 좋아지지 않는다 📉 **[근거 문헌 2026-04-23, 30일 창 밖]**

리즈닝 강도를 3티어로 놓고 **5개 모델 × 3티어 × 60과제 = 900과제**를 3회 다수결로 측정한 벤치마크다. 결과가 균일하지 않다.

| 과제군 | low→high 변화 | 최적 티어 |
|---|---|---|
| 수학(AIME 2026) | **+18~22pt** (가장 가파름) | high — 정답이 이진이라 비용 정당화 |
| 분석(GPQA Diamond) | +12~15pt | medium~high |
| **코드(Expert-SWE 리팩터)** | **+3~5pt에 그침** | **medium — high는 과잉엔지니어링 회귀** |

**비용과 지연은 그만큼 오르지 않는다 — 훨씬 더 오른다.** high는 low 대비 **비용 4~17배**, 첫 토큰 지연은 low 0.4~1.5초 → medium 4~12초 → **high 18~90초**다.

가장 실무적인 발견은 **고효율의 회귀**다. **high 실행의 23%가 과잉 엔지니어링**을 냈다 — 무관한 함수를 개명하고 타입 시그니처를 깨뜨렸다. 즉 코딩처럼 **외부 제약이 있는 작업에서 과도한 리즈닝은 부채**다.

**보조 근거(독립 가이드, 2026-03-27 발행·08-01 갱신)**: 리즈닝 티어별 토큰 배수를 `minimal` 0.1× / `low` 0.3× / `medium` 1× / `high` 3~5× / `xhigh` 8~15×로 정리하고, **"다중 에이전트에서는 오케스트레이터 high, 실행자 low를 쓰면 토큰 50~70% 절감"** 을 권한다. 티어 대응은 `minimal`=개명·포맷·한 줄 수정, `low`=보일러플레이트, `medium`=대화형 기본값, `high`=다중 파일 리팩터·복잡 디버깅, `xhigh`=장기 자율 과제·심층 감사.

**Personal Stack 적용**: 기본값을 `medium`에 두고, **올리는 게 아니라 내리는 쪽을 먼저 시도**한다. 특히 리뷰·보일러플레이트·포맷 계열은 `low`~`minimal`로 내려도 손실이 거의 없다.

### 3. 리즈닝은 오케스트레이터에 몰아라 — 서브에이전트 리즈닝은 이득이 없다 🎯 **[arXiv, 2026-01-16 제출·04-13 개정]**

사용자 질문("고급+낮은 리즈닝 vs 저급+높은 리즈닝")에 **가장 직접적으로 답하는 문헌**이다. 작은 모델들의 다중 에이전트가 훨씬 큰 단일 모델을 이길 수 있는지를 사실 검색·다중 홉 추론·과학 QA·수학 네 과제군에서 비교했다.

핵심 결과 세 가지.

1. **작은 다중 에이전트가 큰 단일 모델을 이길 수 있다** — 후자가 도구에 직접 접근할 수 있는 경우에도.
2. **이득은 오케스트레이터 리즈닝에서 나온다.** 오케스트레이터 수준의 리즈닝이 **가장 큰 향상**을 냈다.
3. **서브에이전트 리즈닝은 이득이 제한적이거나 음(-)이었다.** 시스템 성능은 **서브에이전트 용량이 아니라 오케스트레이터 용량**에 좌우된다.

논문의 결론은 *"개선된 에이전틱 성능은 원시 모델 스케일링보다 아키텍처적 오케스트레이션에 더 의존한다"* 이다.

**즉 "저급 모델 + 높은 리즈닝"을 실행 계층에 까는 것은 근거가 없다.** 리즈닝 예산은 위로 올리고, 아래는 싸고 빠르게 두는 편이 맞다. #2의 "실행자 low로 50~70% 절감"과 방향이 같고, 07-31 #3(`pilotfish`)·오늘 #6(`fable-advisor`)이 구현한 배치와도 일치한다.

### 4. 보이지 않는 오케스트레이터 — 출력만 보면 탐지되지 않는 리스크 🕳️ **[arXiv, 2026-03-17 제출]**

## 오늘의 스택 시사점

1. **리즈닝은 올리지 말고 내려 보라.** #2의 곡선은 medium 위에서 급격히 체감하고, 코드에서는 **high가 오히려 23% 확률로 회귀**를 낸다. 기본값을 `medium`에 두고 리뷰·보일러플레이트·포맷은 `low`~`minimal`로 내리는 것이 첫 수순이다. 올리는 것은 수학·장기 자율 과제처럼 **정답이 이진이고 비용이 정당화될 때만**.
2. **리즈닝 예산은 위로, 실행은 아래로.** #3이 실증한다 — 서브에이전트 리즈닝은 이득이 없거나 음(-)이고, 성능은 오케스트레이터 용량에 좌우된다. **"저급 모델 + 높은 리즈닝"을 실행 계층에 까는 조합은 근거가 없다.** #6·#8·#9가 이 배치를 설정 파일만으로 구현하므로, 셋 중 하나를 골라 그대로 시작할 수 있다.
3. **계층을 쓰되 조율자를 숨기지 마라.** #4는 보이지 않는 조율이 **출력 기반 평가로는 탐지되지 않는** 내부 왜곡을 만든다는 것을 사전등록 실험으로 보였다. **"산출물이 멀쩡하다"를 안전 근거로 쓰지 말 것.** #8이 자식 생성 전에 역할·모델·티어·리즈닝·사유를 공개하는 것은 값싼 대응이며, `model-downgrade-eval`의 판정 규칙에 **"조율 구조를 로그에 남긴다"** 를 추가할 근거가 된다.
4. **라우팅의 진짜 위험은 비용이 아니라 조용한 품질 저하다.** #3 보조 근거가 지적하듯 저하는 대시보드가 아니라 **며칠 뒤 티켓으로** 나타난다. 대응은 라우팅 변경 전 **50~500 대표 케이스 CI 평가 게이트**이며, 이는 사용자의 `model-downgrade-eval`이 이미 규정한 "판정 규칙 사전 등록 → A/B → 프로그램 채점"과 같은 절차다.
5. **가장 시의적절해 보이는 것을 가장 의심하라.** #1은 이 리포트가 닷새간 권해 온 주제의 이름표를 정확히 달고 나타났다. 오늘 채택한 6건도 예외가 아니어서 **전부 저장소·계정 스캔을 거쳤고**, 5건에서 나온 플래그는 전부 오탐으로 판정했다. 스캔 없이 별 수만 보고 받아들이지 말 것.
