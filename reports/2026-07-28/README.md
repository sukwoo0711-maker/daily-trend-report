## 상세

### 1. MCP 2026-07-28 스펙 최종 발행 — 세션이 사라진다 🔌
**07-27 이월 open query 2가 이 판에 명시적으로 넘긴 항목이다** — 어제 리포트는 *"07-28 상태 비저장 코어 정식판이 나온다. 스펙 자체는 07-21 #1에서 다뤘으므로 순위 제외하되, **정식 릴리스 후 마이그레이션 영향만 다음 판에서 재평가**"*라고 적었다. 그 지시대로 **최종화 + 구체 변경/마이그레이션 영향**만 다룬다(개정 예고=07-21 #1, 채택 규모 수치=07-24 #4는 이미 소진). 공식 블로그는 RC를 5/21에 락한 뒤 *"The final specification will be published on July 28, 2026"*라고 명시한다. 핵심은 **프로토콜 레벨 세션 제거**다: `initialize`/`initialized` 핸드셰이크와 `Mcp-Session-Id` 헤더가 빠지고, 모든 요청이 자기완결적(self-contained)이 되며 메타데이터는 각 요청의 `_meta`로 이동한다. 라우팅용 `Mcp-Method`·`Mcp-Name` 헤더가 필수가 되고, 상태는 애플리케이션이 툴 파라미터·핸들로 명시 관리한다. 부가로 **MCP Apps**(샌드박스 iframe의 서버 렌더 UI), **Tasks 확장**(실험적 코어 → 확장 이관, 재설계된 라이프사이클), **OAuth/OIDC 정렬 강화**(`iss` 검증 의무화 등 6개 SEP), **12개월 최소 deprecation 창을 둔 정식 feature-lifecycle 정책**이 들어온다. Personal Stack 관점: **셀프호스팅 MCP 서버가 sticky 세션·공유 세션 저장소·게이트웨이 DPI 없이 평범한 round-robin 뒤에서 돌 수 있게 된다**(스케일·운영 단순화). 단, **2026-07-28 리비전 서버는 구 클라이언트와 상호운용이 깨질 수 있으므로**(양쪽이 지원 era를 공유하거나 폴백/번역을 구현해야 함), 오늘 이후 MCP 스택을 만지고 있다면 **업그레이드/호환 경로부터 확인**해야 한다. 어제 #2(llama.cpp 로컬 MCP)까지 겹쳐 보면, 로컬 모델이 MCP 도구 생태계에 붙는 시점에 프로토콜 바닥이 상태 비저장으로 재편되는 것 — 로컬·셀프호스팅 스택에 특히 유리한 방향이다.
- 1차 출처: [MCP 공식 블로그 — 2026-07-28 Specification](https://blog.modelcontextprotocol.io/posts/2026-07-28-release-candidate/), [Beta SDKs for 2026-07-28](https://blog.modelcontextprotocol.io/posts/sdk-betas-2026-07-28/)
- 보조 출처: [TechTimes(7/27) — "Drops Sessions Tomorrow"](https://www.techtimes.com/articles/321671/20260727/ai-tool-protocol-drops-sessions-tomorrow-mcps-largest-spec-change-since-launch.htm), [4sysops — stateless·routable headers·authz hardening](https://4sysops.com/archives/2026-07-28-model-context-protocol-mcp-stateless-multi-round-trip-routable-headers-authorization-hardening/), [Developers Digest — 마이그레이션 가이드](https://www.developersdigest.tech/blog/mcp-2026-07-28-breaking-changes)
- 반대 근거/한계: 07-21 #1의 **후속(최종화)**이라 주제 자체는 이미 다뤘다 — 07-27이 명시적으로 이 판에 이월했고 "마이그레이션 영향만" 신규로 취급한다. "오늘 최종 발행"은 공식 블로그의 발행일 명시에 근거하나, 작성 시점에 실제 페이지가 RC→Final로 전환된 바이트를 직접 재확인하지는 못했다(공식 명시 발행일 신뢰).

### 2. "코딩은 해결됐다는데 왜 소프트웨어는 더 나빠지나?" — AI 코딩 품질 논쟁 🧩
7/24 게시된 에세이 "Nothing Works and Everyone Is Euphoric"가 *"If coding has been solved, why does software keep getting worse?"* 제목으로 HN에서 크게 붙었다(**880pt·679댓글**). AI가 코드 **생성량**은 늘렸는데 체감 품질은 오히려 나빠진다는 역설을 다룬다. 상위 논의는 원인을 "AI 그 자체"보다 **구조**로 돌린다 — 대형 제품팀에서 아무도 무엇을 소유하지 않고 내부 목표 정렬이 약할 때 품질이 무너진다는 지적(*"A lot of the product misses come from large product teams where nobody owns anything, and where there's minimal internal goal alignment"*, HN 상위 코멘트 *hibikir*), 그리고 "10년 전에도 같은 걸 느꼈다, AI와 무관하다"(*AussieWog93*)는 반론이 나란히 달렸다. Personal Stack 관점의 교훈은 명확하다: **에이전트로 생성량을 늘려도 품질은 리뷰 규율·소유권·정렬에서 나온다.** 이는 어제 07-27 #1(컨텍스트 덜어내기)과 07-23 #6("하네스 > 모델")·07-23 #10(CS 기본기 논쟁)과 같은 결의 방법론 신호로, "생성 자동화"보다 "검증·소유 루프"에 스택 투자를 배분하라는 실천 지침으로 읽힌다.
- 1차 출처: [Hacker News — 토론 스레드(#49033004)](https://news.ycombinator.com/item?id=49033004)
- 보조 출처: [원문 에세이 — ptrchm.com "Nothing Works and Everyone Is Euphoric"](https://ptrchm.com/posts/nothing-works-and-everyone-is-euphoric/)
- 반대 근거/한계: **의견 스레드**이므로 일반화 주의(주관적 품질 인식·노스탤지어 편향 병존). HN Algolia API가 코멘트별 득표수를 노출하지 않아 **상위 코멘트의 정확한 표수는 미표기**(스레드 내 순위 위치로만 "상위"라 표기).
- 신뢰도: 중간 — 스레드 실재·참여도·게시일은 원문으로 확인, 주장은 의견성.

## 오늘의 스택 시사점

1. **오늘 당장: MCP 스택이라면 호환 경로부터 점검.** #1로 오늘 세션이 사라지는 최종 스펙이 발행된다. 셀프호스팅 MCP 서버는 게이트웨이 세션·sticky 라우팅을 걷어낼 기회지만, **구 클라이언트와 상호운용이 깨질 수 있으므로** 업그레이드는 양쪽 era 정렬/폴백을 확인한 뒤 진행할 것. 재작성 없는 부분은 헤더 라우팅(`Mcp-Method`) 정도라 이식 부담은 낮은 편. 어제 #2(로컬 MCP)와 합치면, 로컬 스택에 MCP를 붙일 최적 시점이 이번 주다.
2. **생성이 아니라 소유·검증에 투자하라.** #2 논쟁의 결론은 "AI 생성량↑ ≠ 품질↑"이다. 개인 스택 설계도 같다 — 에이전트가 코드를 더 많이 쏟아내게 만드는 스킬보다, **리뷰·테스트·소유권을 강제하는 스킬/훅**(예: 07-24 #2 Superpowers류의 TDD 강제, 승인 훅)이 ROI가 크다. 어제 #1의 "컨텍스트 덜어내기"와도 같은 방향 — 스택은 **더 쌓는 것이 아니라 덜고 조이는 것**이 이번 주 일관된 메시지다.
3. **참고(추천 아님): 보안 스캔의 하네스 내재화 흐름.** 게이트로 제외한 Anthropic Claude Security 플러그인처럼, 취약점 스캔을 **커밋 전 하네스 안**에서 돌리려는 흐름이 보인다. 다만 라이선스·과금이 불명이라 이번엔 추천하지 않는다 — 개인 스택에선 당분간 무료·오픈 라이선스의 무설치 스캔 수단을 우선 검토할 것.
